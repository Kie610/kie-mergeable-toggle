# 隠している間のコストの再検討（2026-09-02）

2026-08-30 の決定 D1「新しい隠し機構・統合機構は作らない」（`Docs/hidden-cost-decision.md`）を、
ユーザーの明示指示で開き直した。**改善案を幅広く出し、比較し、見込みのあるものを実測して、採用候補を決める。**

**経過**: 最初に実装・実測した案 1a（初期非表示トグルをゲート付き別レンダラーへ統合）は、
グループが全部隠れた状態でしか効かず、SMR とスロットの統合効果も一部手放すため、
**ユーザー判断で却下した**（§3、§4.3）。実装は取り消した。

**採用候補（§4.4 の実測に基づく）**: **隠れたマテリアルスロットの差し替え**（案 P2）。
統合メッシュの各スロットについて、そのスロットの全頂点を覆う隠蔽シェイプ（所有トグル）が全部隠れたら、
マテリアルを「描画されないシェーダ」へ差し替える。SMR もスロット数も増えず、隠れたスロットの
draw call と頂点シェーディングが消える。効く粒度は「マテリアルの共有単位」で、
衣装セットごとにマテリアルが分かれているアバター（MUMUS_all）では普段の状態（半分隠す）の損が消え、
衣装 7 点が 1 マテリアルのアバター（Shinano）では全部隠したときだけ効く。
**2026-09-03 に 0.9.0-alpha として実装した**（`emptyHiddenMaterialSlots`、既定 ON。§4.7 に検証結果）。

確定度は C（確認済み）/ A（仮定）/ U（未解決）で示す。数値はすべて出典付きの実測値で、
実測していないものは「未測定」と書く。

## 1. 問題の正体（前回までの実測の要約）

- C: 症状の正体は「**隠しても安くならない**」である。変換なし A は
  隠すほど速くなる（wall 11.776 / 7.765 / 6.945 ms、全表示 / 半分 / 全隠し、10 体・run6）が、
  変換あり B は平ら（10.541 / 10.268 / 10.298 ms）。差は取り逃した利益である
- C: VRChat PC の GPU スキニング経路で、全隠しの損の主因はスキニングではない。
  CPU メインスレッドの損は統合メッシュが常に持つ**レンダラー 1 個とマテリアルスロット**
  （目標 F で、変換したまま残る頂点を 93% 減らしても d が横ばい）、
  wall / GPU の損は**毎描画シェーディングされる頂点**（F で頂点数に応じて減る）
- C: 統合メッシュには常時表示のメッシュ（素体）が同居するので、「全部隠れたらレンダラーを切る」
  条件が存在しなかった。これが前回「レンダラー無効化」を却下した理由

## 2. 今回の調査で新しく分かったこと

ウェブ調査（サブエージェント 3 本、英語 + 日本語 15 通り）とローカルソース検分の結果。

- C: **AAO の自動統合は、`m_Enabled` が同じ AnimationLocation 集合でアニメーションされた
  レンダラー群を activeness 付きで統合し、統合後のレンダラーへ `m_Enabled` のアニメーションを
  引き継ぐ**（AAO 1.9.17 `AutoMergeSkinnedMesh.cs` L297–360 `MergeAnimatingSkinnedMesh`、
  `keepPropertyCount: 2`、超過分は中間 GameObject で吸収）。本パッケージが自前のレイヤーの
  同じステートで複数レンダラーの `m_Enabled` を動かせば、AAO はその群を素体とは別の
  1 レンダラーへ統合してくれる。**本パッケージ側に統合の実装は要らない**
- C: 「既定の表示状態で統合グループを分ける」発想は主要ツールに既にある。
  d4rkAvatarOptimizer の **Keep Default Enabled State**、AAO 手動 Merge Skinned Mesh の
  **有効無効状態が統合先と異なるレンダラーを統合しない**（ビルド時の静的判定、1.8.0 から既定 false）。
  どちらも見た目と安全側を理由にした機能で、既定状態を分割の信号に使う前例になる
- C: anatawa12 は AAO issue #1526（2025-10-04、日本語）で NaNimation / Infinimation を
  5 つの理由で見送っており、そのうち 1 つが本件そのもの
  （「T&O へ入れると別メッシュとして非表示にしていた場合より頂点シェーダの呼び出しが常にかかる」）。
  ただし「頂点シェーダ負荷は多くの場合小さいので気にしなくてよい可能性も十分ある」と併記し、数値は無い。
  AAO 1.9.18（2026-08-31）時点で activeness が異なるメッシュを統合する機能は無い
- C: Unity 公式は「マテリアル未割り当てのサブメッシュはビルドでもエラーシェーダで描く」と明記
  （null マテリアルで描画を省く案は不成立）。「マテリアルがサブメッシュより少ない場合」の挙動は
  公式に記述が無い
- C: GPU スキニング経路のブレンドシェイプは、ウェイト非 0 のシェイプごとに compute dispatch 1 回、
  デルタ非ゼロの頂点だけを処理する（d4rkpl4y3r の計測ノート。Unity 2023.1 のバッチ化の存在が
  2022.3 での個別 dispatch の傍証）。成分③はシェイプ本数 × 影響頂点数で決まり、削る余地が無い
  という前回の結論はそのまま
- C: `SkinnedMeshRenderer.m_Mesh` をアニメーションで差し替えるギミックは、日本語・英語とも
  実例が見つからない（MeshFilter の差し替えは AAO 1.9.18 が対応した実例あり）。
  可否・ブレンドシェイプ index の整合・差し替え時のヒッチはいずれも U
- A: Unity 2022.3 の `PlayerSettings.gpuSkinning` は対応 Android API を GLES3.1 のみと列挙し
  Vulkan を含めない。Quest（Vulkan）では CPU スキニング経路の可能性がある（未実測。目標 G の前提）
- C: 日本語圏には「統合したメッシュは隠しても軽くならない」を明文化した記事が無く、
  実測値を出した記事もゼロ。定番の対処は「オンオフしたい単位でまとめて統合する」

## 2b. 0 から列挙し直した案（現行実装を土台にしない）

§3 の 18 案は現行の infinimation と AAP ゲートの延長で出したものだった。ユーザーの指摘を受けて、
「GPU / CPU が実行時に何を省けるか」という原理から列挙し直す。省ける単位（粒度）で分類する。

| 粒度 | 実行時に省く手段 | Animator から動かせるか | 案 | 粒度の副作用 |
| --- | --- | --- | --- | --- |
| レンダラー | `m_Enabled` / GameObject active | 可 | 1a（却下）、統合しない（A） | 粗すぎる。SMR を分けるとランク項目が増える |
| **マテリアルスロット** | **描画パスを持たないマテリアルへ差し替え**（PPtr カーブ） | **可** | **P2: 隠れたスロットの差し替え** | 粒度 = マテリアル共有単位。共有を断つ（P2b）とスロット数が増える |
| サブメッシュの index 範囲 | `Mesh.SetSubMesh` / index buffer | 不可（スクリプト無し） | — | — |
| メッシュ全体 | `m_Mesh` の PPtr 差し替え（状態ごとの変種） | 可 | P3: メッシュ変種 | 変種数が 2^g、VRAM、切替ヒッチ、実例なし |
| 頂点 | ブレンドシェイプで遠方 / 退化 | 可 | 現行（infinimation）、P5: 一点へ潰す | 頂点シェーダは走る。draw call は残る |
| 頂点（シェーダ内） | シェーダで頂点を捨てる（UV タイル破棄等） | 可（マテリアル値） | 退役済み | 頂点シェーダは走る。シェーダ依存 |
| パス | 影・輪郭線パスの無いマテリアルへ差し替え | 可 | P2 の劣化版 | P2 が上位互換 |
| なし | 何もしない（前回 D1） | — | 14 | 既定 OFF 衣装の損を払い続ける |

**P2 を軸にした変種**:

- **P2a: 統合したスロットのまま差し替える**（スロット数を増やさない）。所有トグルが 1 つなら
  そのトグルのクリップへ PPtr カーブを足し、複数なら AAP の AND ゲートで差し替える。
  効く粒度はマテリアル共有単位
- **P2b: トグルごとにマテリアルを複製して共有を断ってから差し替える**。差し替えがトグル単位で効くが、
  AAO がスロットを統合しなくなるのでスロット数（ランク項目）が統合前へ戻る。利用者の選択肢として
  提供する価値があるかを実測で決める（§4.4 の S3 / S4）

**この列挙で新しく気付いたこと**: 実行時に Animator から動かせる「省く手段」は、レンダラー・
マテリアルスロット・メッシュ・頂点の 4 段しか無く、粒度と代償は上の表のとおり一意に決まる。
ランク項目（SMR 数・スロット数）を増やさずに draw call を止められるのはマテリアルスロットの
差し替えだけである。

**1a を選ぶ理由（前回の却下理由との突き合わせ）**

- 前回「レンダラー無効化」を却下した理由は「統合先に常時表示のメッシュが同居する」だった。
  1a は初期非表示トグルだけを素体から分けるので、**無効化してよいレンダラーが存在する**
- 前回「OR ゲート」を却下した理由は「全トグルが同時に隠れている状態でしか効かない」だった。
  1a はゲートの単位を「初期非表示のトグル群」に絞るので、**アバターの既定状態がそのまま
  「全部隠れている状態」になる**。既定状態は利用者が最も長く居る状態である
- 前回「既定を変える」を却下した理由は「`activeSelf` は『よく着るか』を意味しない」だった。
  1a に必要なのは「よく着るか」ではなく「既定でどう見えるか」で、それは `activeSelf` そのものである。
  外れた場合（既定 OFF の衣装を常に着る利用者）の損は SMR +1 ぶん
  （レンダラー単価 1.25 µs/体/描画、目標 B）に留まる
- d4rk と AAO 手動統合が同じ信号で分割している（§2）

## 4. 実測

§4.1〜4.3 は案 1a（却下）の検証記録、§4.4 が採用候補 P2 の実測である。

### 4.1 案 1a の E2E（AAO の統合が期待どおり起きるか）

ハーネス `avatar-dev/Assets/_MTLab/Editor/MTHiddenGroupE2E.cs`（gitignore 対象）。
Shinano / MUMUS_all / CustomBase を OFF / ON / ALL（両方向のクリップを持つトグルを全部
初期非表示にして ON）の 3 通りで実ビルド（AAO 込み）し、レイヤーが束ねる SMR が 1 個以上できること、
その SMR がシリアライズ時点で無効（enabled=false または GameObject の activeSelf=false）であること、
メンバーの隠蔽シェイプがその SMR 群にだけ過不足なくあること、SMR 数が OFF+1 以下で三角形数が
不変であることを検査する。結果は `avatar-dev/MTLabOut/hidden_group_e2e.txt`。

実測で分かった実装上の事実（C）:

- **AAO は引き継ぐ activeness プロパティが 1 本だと、統合先 GameObject の `m_IsActive` へ割り当てる**
  （`MergeAnimatingSkinnedMesh` は末尾から 1 本目を GameObject の active、2 本目を Renderer の
  enabled へ写像する）。本パッケージは SMR の `m_Enabled` を動かすが、統合後のカーブは
  `GameObject '$$AAO_AUTO_MERGE_SKINNED_MESH_n' m_IsActive` になり、統合先 GameObject は
  `activeSelf=false` で出る。機能上は GameObject ごと非アクティブになるので、描画も頂点処理も止まる
- 統合できないメンバー（MUMUS_all の `Body_hand`: マテリアル差し替え持ち）は元の SMR のまま
  `m_Enabled` のバインディングで残り、同じレイヤーで無効化される
- **ALL の構成は「両方向のクリップを持つトグル」にしか適用できない。** Shinano の初期表示トグル
  7 個は FX に隠すクリップしか持たず、表示側は Write Defaults の書き戻しに頼っている。
  検証で初期非表示へ変えると表示する手段が無くなり、AAO の `AutoFreezeNonAnimatedBlendShape` が
  隠蔽シェイプを「アニメーションされていない」として凍結した（トレースで確認。元の `m_IsActive`
  でも同じ構成なら永久に表示されないので AAO の判断は正しい）。**製品の機構は元から初期非表示の
  トグルだけを対象にするので、この問題を踏まない**（元の作者が表示側のクリップを用意している）。
  ハーネス側で ALL のメンバーを両方向クリップ持ちに限定した

### 4.2 案 1a の負荷（系列 G0 / G1）

  更新を間引く）だった（ユーザーの観察「ウィンドウをアクティブにすると走り始める」）。検査の入口で

**ビルド時間**（GUI Unity、差し替え ON / OFF）: Shinano 4.4 / 2.9 s、MUMUS_all 3.7 / 3.1 s（最適化 ON）。
パス自体は batchmode のログで 17〜48 ms（Milfy 1.6 s）。

**製品ビルドでの性能再測定は行っていない。** 差し替えるスロット集合は §4.5〜4.6 の系列 S / W で
ハーネスが差し替えたものと同じ規則で、静的検査がその一致（Shinano 1 / MUMUS 11）を確認している。

## 5. 決定

- **D1（改）: 案 1a は却下。案 P2（隠れたスロットの差し替え）を採用候補とし、製品へ実装する。**
  実装の形は §6。実装後に E2E と同じ系列 S で効き目が模倣どおりかを確かめてから採用を確定する
- **P2a（統合スロットのまま差し替え）を既定にする。** SMR もスロット数も増えないので、
  効かない場合でも損が無い。P2b（トグルごとにマテリアルを分ける）はスロット数（ランク項目）を
  増やすので、§4.5 の実測で表示中の損と隠蔽中の得を並べたうえで、利用者の選択肢として出すかを決める
- D2〜D5 は変えない
- 1a のコードは取り消した（差分は `avatar-dev/MTLabOut/rejected_1a_separateInitiallyHiddenToggles.patch`）

## 6. 実装計画（P2a）と公開契約への影響

- 第 2 パスを `BuildPhase.Optimizing` の `AfterPlugin("com.anatawa12.avatar-optimizer")` に置く
  （AAO の自動統合は PPtr アニメーションを持つレンダラーを統合しないので、統合の後に差し替えを足す）
- 統合メッシュの各サブメッシュについて、頂点を覆う隠蔽シェイプ（`MT_Hide_*` を含む名前。デルタ非ゼロの
  頂点で判定）の集合を所有トグルとする。覆われない頂点を含むスロットは対象外
- 所有トグルが 1 つ: そのトグルのクリップ（`blendShape.<統合後の名前>` のバインディングで引く）へ
  `m_Materials.Array.data[i]` の ObjectReference カーブ（表示 = 元マテリアル、非表示 = `MT_Empty`）を足す
- 所有トグルが複数: 共有 PB 停止と同じ AND ゲートのレイヤー（`MT_SlotOff <n>`）を作り、その Active /
  Stopped クリップに PPtr カーブを置く。AAP `MT_Hidden/<パス>` は第 1 パスで全変換トグルに作っておく
- `MT_Empty` はパッケージ同梱のシェーダからビルド時に生成するマテリアル。Android ビルドでは
  許可シェーダの制約があるので差し替えを生成しない（効かないが無害）
- Safety でシェーダがブロックされた場合はフォールバックで描かれるが、頂点は infinimation で遠方に
  あるので見た目は壊れず、draw call が戻るだけ
- 公開契約: bool フィールド 1 つ（名前は実装時に決める。既定 ON）と、生成物 `MT_SlotOff <n>` レイヤー・
  `MT_Empty` マテリアルの追加。既存フィールド・`MT_Hide_…`・`MT_PBStop`・パッケージ ID は変更なし。
  **破壊的変更ではない**。SMR 数・スロット数は変わらない

**実装結果**（2026-09-03）: bool フィールドは `emptyHiddenMaterialSlots`（既定 ON）。
`MT_Hidden/<パス>` AAP は FX に作れる全変換トグルへ作るようにした。共有 PB のゲートと `MT_SlotOff` は
`AndGateLayer` で共通化。AAO はシェイプ名へ接頭辞に加えて末尾の連番や入れ子の接頭辞を付けるので、
第 2 パスは「`MT_Hide_` 以降が控えた名前で始まる」最長一致で所有トグルを引く。
